# 观复是什么：一次重新对齐

> 这份文档记录 **2026-11-18 那次「把项目完整理解清楚」的问答结论**，
> 它取代之前那份跑偏的「侧车 / 执行端」方案（那份的架构前提已经不成立了）。
>
> 相关的：部署评估见 [DEPLOYMENT.md](DEPLOYMENT.md)；规矩见 `AGENTS.md`；用法见 [USAGE.md](USAGE.md)。

---

## 一、一句话定位

**观复 = 给 AI 开发流程用的「过程记录 + 审批 + 归档」中枢。**

盯住 AI 开发的进度：做到哪一步了、谁做的、哪些操作需要人点头、
过程中产出的文档 / 脚本 / 报告统一归档、到了迭代版本能打包交付。

**它不碰代码，也不关心 agent 到底改了哪几行。**
代码是 agent 用自己的客户端工具改的，观复只记「这件事发生了、结果是什么」。

---

## 二、给谁用、怎么隔离

| 层 | 口径 |
|---|---|
| 部署 | 一个部署 = 一个团队（一个数据目录 = 一个租户） |
| 团队成员 | 人（成员 / 管理员）与 agent 共处同一个团队 |
| 可见性 | 普通成员**只看自己的东西**；管理员看**全部** |
| 分配 | 管理员可以**把任务分配给别人** |
| 认领 | **未分配**的任务，任何成员都可以自己认领 |
| 审批 | 默认**本人批自己的**；**管理员可以代批**，但必须写明代批理由 |

> 这一版把原来「工作区 = 租户」推进了一步：租户边界仍是「一个部署」，
> 但租户**内部**有了成员身份、角色与个人可见性 —— 这就是「个人数据隔离」落地的位置。

---

## 三、观复管什么

1. **进度**：任务、状态机、看板、调度板（「现在什么能干」「先干哪个」）。
2. **操作留痕**：谁在什么时候动了什么，串成可验的审计链。
3. **人工审批**：观复**自己提供的**危险能力（主要是数据库相关操作）必须过人眼。
4. **归档**：文档与产物**两套都留**，统一挂在任务与迭代版本下。
5. **交付**：按迭代版本勾选要交付的东西 → 下载 **一个 zip + 清单**。

---

## 四、观复不管什么（作废清单）

这几条是「本地设计」时代为「代码在观复旁边」而存在的，
现在前提没了，它们**要么作废，要么降级为一条信息**：

| 作废项 | 原因 |
|---|---|
| **产出采集**（推进到 Review 时快照工作区） | 观复不碰代码，也不需要「这个任务改了哪些文件」 |
| **分支守卫**（领活 / 推进 InDev / 启动 agent 时校验分支） | 同上 —— 分支是 agent 自己仓库的事 |
| **工位 / worktree 登记与独占** | 并行由 agent 自己开 worktree 解决，观复不替它管目录 |
| **仓库路径绑定作为权限边界** | 仓库路径降级为**项目的一条信息**（给人看），不再当作用域硬边界 |
| **评审里的「变更文件列表」** | 观复不判代码，评审只看 agent 交上来的报告 |

**保留的**：任务、状态机、审计、审批、文档与产物、调度、规约、评审（只看结论不看代码）。

---

## 五、评审：退回到「本地辅助」

评审**不在服务器上做代码评审**。它保留的是**流程与结论的载体**：

- 七个维度的定义与检查清单 —— 给 agent 在本地自评时用；
- 工具可以做成 CLI 提供（本地跑），也可以由 agent 自己 review 后交一份报告；
- 观复只**存结论**（谁评的、过了没过、证据是什么），不判代码质量。

---

## 六、审批的新边界

**审批批的是「观复提供的功能」，危险的是数据库操作。**

| 要审批 | 不审批 |
|---|---|
| `db_execute`（写库）、删库改表这类 | agent 在本地改代码、写文件、跑自己的工具 |
| 其它会改动共享状态的操作 | agent 的本地 git 操作 |
| —— | agent 交上来的文档 / 脚本归档（除非涉及生产发布口径） |

审批继续绑在**具体操作**上（工具 + 参数指纹 + 项目），
一条批准只能用一次，换个 SQL 就对不上 —— 这条规矩不动。

---

## 七、归档与交付

### 归档：两套都留

| 套 | 装什么 | 现在缺什么 |
|---|---|---|
| **文档** | 需求、设计、说明、**交付文件** | 类别要补「交付文件」；**查看必须渲染好的**，不给原始 md |
| **产物** | 脚本（**SQL 脚本**）、报告等 | 类型要补「SQL / 脚本」；产物**要能改**（人改 AI 写的脚本），改完**留痕** |

### 交付：按迭代版本打包

- 层级是 **项目 → 迭代版本（里程碑）→ 任务**；
- 候选池 = 该迭代版本下的文档 + 产物；
- 人**勾选**要交付哪些 → 下载 **一个 zip + 一份清单**（清单写明带了什么、来自哪个任务、什么时间）；
- 打包这件事本身要**留痕**（谁在什么时候打了什么包）。

## 八、身份与隔离：谁怎么进来

### 8.1 两类身份，两条接入线

| 谁 | 怎么进来 | 服务端认出他是谁 |
|---|---|---|
| **人** | Web 界面**登录**（账号 + 密码） | 成员记录（用户名 / 角色 / 状态） |
| **agent** | **MCP**（HTTP `/mcp` 或 `guanfu mcp` stdio 桥接）+ `X-Guanfu-Token` | 凭证记录（agent 标识 + 归属成员） |
| **脚本 / CI** | REST + 同一把凭证 | 同上 |

> 人**不走 MCP** —— MCP 是给 agent 的机器接口。
> 人用界面；agent 用 MCP；两条线在服务端汇成同一个「当前身份」。

### 8.2 绑定关系

```
成员（人） ──1:N── agent 凭证 ──N:1── agent 运行（MCP 会话）
```

- 一个成员可以有多把 agent 凭证（Claude Code 一把、Codex 一把）；
- 成员停用 → 名下凭证立即失效；agent 凭证可单独吊销，不用动人的账号；
- 成员改密码不影响正在跑的 agent；
- 凭证的可见范围 = 所属成员的可见范围（再收窄到指定项目）。

### 8.3 人怎么登录（**已做**，v0.23）

- **账号 + 密码**（自管，无外部依赖；ASP.NET Core 自带 cookie 认证）：
  `POST /api/auth/login` → 签名 cookie（HttpOnly / SameSite=Strict）→ 请求带上成员身份。
- **密码存哈希**（PBKDF2-HMAC-SHA256 + 每人一个盐），不存明文；管理员可重置成员密码。
- **现有的 `.human-token` 不作废**：它是**引导凭证** —— 本机用它把第一个管理员账号建出来，
  建完就可以改密码。之后它只保留「本机引导 / 紧急恢复」用途。
- **停用成员 → 名下的凭证立刻作废**（「人走了，钥匙还在」是团队部署最大的洞）。
- 单人本机用法**完全不变**（没建成员表时，仍是「一个人 = 全部可见 = owner」）。

### 8.4 成员怎么进来（接入流程，**已做**）

1. 管理员在界面建成员：用户名 + 初始密码 + 角色（成员 / 管理员）；
2. 成员首次登录改密码；
3. 成员（或管理员）签发 **agent 凭证**：选「归属成员」+ 填 agent 标识（如 `claude-code`）+ 可见项目；
4. 成员把 `/connect` 页生成好的配置片段里的 `<凭证>` 换成实际 token，粘进 Claude Code / Codex；
   这把 token 就是「这台机器上的这个 agent 属于我」的唯一绑定凭据。

> agent 的**显示名**可以沿用本地 git 的 `user.name`（连上时带过来），
> 但**身份以凭证为准** —— 请求头里的名字谁都能填，只当显示用。

### 8.5 数据模型要动的

| 改动 | 说明 |
|---|---|
| `Member`（新表） | 用户名（唯一）、显示名、角色（成员 / 管理员）、密码哈希、状态 |
| `AccessCredential.MemberId`（新列） | 凭证归属成员；`Kind = Agent` 的凭证必填 |
| `Task.Assignee` → 指向成员 | 现在是自由文本（人名或 agent id），改成指向成员（可为 agent） |
| `Approval.DecidedById` / `DecidedOnBehalfOfId` / `DecisionReason` | 实际裁决人、被代人、代批理由 |
| 可见性服务（新） | 按身份过滤任务 / 文档 / 产物 / 审批列表；**界面与 MCP 工具两侧都要过** |
| 登录端点 + cookie | `/api/auth/login` / `/logout`；敏感端点的门禁从「共享 token」升级为「成员角色」 |

### 8.6 审批的归属与代批

- 审批默认落到**发起者本人**名下（不是落到 admin 名下）；
- **管理员可以代批**，但必须填**代批理由**；
- 记录同时写「实际裁决人 = 管理员」「被代人 = 发起者」「理由」，审计里也留一份 ——
  代批是合法的，但必须**看得见是谁替谁批的**。

---

### 8.7 还没做的（v0.23 之后的下一片）

- **可见性过滤**：普通成员只看自己的东西（任务、文档、产物、审批）—— **还没做**。
  现在所有有权限的人看到的仍是同一份看板。
- **任务分配与自认领**：管理员能把活分给别人；未分配的活人能自己认领。
  —— 认领机制已有（`Task.ClaimedByAgentId` + 租约），但**分派给成员**还没接上。
- **管理员代批**：审批默认落在发起者名下；管理员能代批，但必须写理由。
  —— 审批的归属字段还没加。

## 九、诚实边界

- **观复不判代码质量**：评审结论是 agent 自评 + 人签字，观复只保证「谁说的、什么时候说的」可追溯。
- **审计链头归档仍是部署方的责任**：观复挡不住「拿到库文件的人连哈希一起重算」。
- **可见性不是安全边界的一半**：界面过滤做了，但 MCP 工具侧必须同样过一遍才算数。
- **交付包是打包那一刻的快照**：之后的改动不会自动进去（清单里带时间戳）。

## 十、路线（四步）

| 步 | 做什么 | 为什么是这个顺序 |
|---|---|---|
| **0. 归档交付线** | 文档渲染查看、产物可编辑 + 留痕、类型补 SQL/脚本、类别补交付文件、按迭代版本勾选打包 → zip + 清单 | **回到初心**：这是观复最不可替代的价值，且不依赖身份改造 |
| **1. 身份与隔离** | 成员表、角色、登录、可见性过滤、分配与认领、审批归属 | 让「小组共用」真的成立 |
| **2. 砍清单** | 作废产出采集 / 分支守卫 / 工位 / 仓库路径绑定降级、评审去掉变更文件列表 | 砍完产品才干净；放最后是因为砍完会更依赖第 0 步的交付体验 |
| **3. 商业化最后一层** | 多租户隔离、计费、审计导出 | 现在做是浪费 —— 先把单团队跑顺 |

> 每步都要跑 `./tests/verify.sh`；改了 MCP 工具或审批闸门要跑端到端七条链路。

---

## 十一、还要你确认的

1. ~~管理员能不能替别人批审批？~~ → **能**，但必须写代批理由，审计里留「谁替谁批」。
2. **未分配的任务对全员可见**（否则没人能认领）—— 这条按「可见」实现。
3. **先做第 0 步还是第 2 步？** 我建议 **先第 0 步**：它让产品立刻回到「盯进度、留记录、能交付」这条主线上，而第 2 步是减法，砍完没有新东西补上会显得更空。
4. **人要不要密码？** —— 我推荐**要**（账号 + 密码，自管）。备选是「只发 token、粘一次就登录」，
   实现更省事但体验差、也没有改密码与吊销的入口。

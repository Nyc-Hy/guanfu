# 团队化改造方案（一个二进制，两个角色）

> 这是一份**完整的改造方案**（2026-11-18 写）。它把「服务器上没有代码」这个前提
> 变成一个可落地的架构，而不是一句口号。
>
> 相关的：评估背景见 [DEPLOYMENT.md](DEPLOYMENT.md)；规矩见 `AGENTS.md`。

---

## 一、一句话

**观复 = 集中的流程与信任中枢 + 装在 agent 旁边的本地执行端。**
一个二进制，两个角色：`guanfu serve`（中枢）与 `guanfu agent mcp`（执行端）。
**单机部署与中央部署给 agent 的工具面完全一样** —— 变的只是代码在哪台机器上。

---

## 二、三个部件

```
   人（浏览器）
      │  看板 / 审批 / 评审 / 审计 / 规约
      ▼
┌──────────────────────────────┐
│ 观复核心（guanfu serve）      │   ← 纯数据 + 流程 + 信任
│  看板 · 规约 · 评审 · 审批    │      **不碰代码**
│  审计账本 · 交接 · 调度 · 凭证  │      可远端、可本地
└──────────────────────────────┘
      ▲                                  ▲
      │ 转发看板类调用                     │ 审批号 / 身份对账
      │                                   │
┌──────────────────────────────┐   ┌─────────────────────────────┐
│ 观复执行端（guanfu agent mcp）│◀──│  agent 客户端（Claude Code…）│
│  文件 · git · shell           │   │  只指向执行端                 │
│  当前分支 · 改动清单          │   └─────────────────────────────┘
│  **在 agent 旁边跑**          │
└──────────────────────────────┘
        │ 用 agent 机器上的仓库
        ▼
   开发者本地 clone / worktree
```

**为什么执行端必须在旁边**：MCP 工具是**服务端执行**的 —— agent 客户端把请求发给 MCP 服务端，
由服务端去动文件、跑 git。所以「代码在哪台机器上」＝「工具在哪台机器上跑」。
要两种部署功能一样，工具就得永远在 agent 旁边。

**为什么核心不该碰代码**：它是团队共享的那一份（看板、规矩、审批、账）。
碰代码就绑死在某台机器上，团队就共享不了。

## 三、工具怎么分（75 个，逐个查过）

| 执行点 | 工具 | 说明 |
|---|---|---|
| **执行端（本地）** | `fs_read` `fs_list` | 读 agent 机器上的仓库 |
| | `git_commit` `git_push` | 提交 / 推送 |
| | `shell_run` | 跑命令 |
| **核心（服务端）** | 看板类 45 个 | 任务 / 里程碑 / 依赖 / 状态机 / 规约 / 评审 / 审批 / 审计 / 交接 / 调度 / 工位 / 用量 / 会话 |
| | 文档类 8 个 | `doc_upload` `doc_parse` `doc_get_*` `doc_list_struck` `doc_search` `doc_list_formats` —— 动的是**观复自己的文档存储**（原件在观复的数据目录，不在仓库里），所以是纯服务端 |
| | 数据库类 6 个 | 数据库通常是共享的，核心直接连 → **审批闸门一行不改** |

**另外两处不是工具、但同样依赖本地 git 的核心逻辑**（最容易漏）：

| 逻辑 | 今天 | 改造后 |
|---|---|---|
| **分支验证**（领活 / 推进到开发中 / 启动 agent） | 核心读 git → 服务器没 git 就全线拒绝 | 执行端读**本地**分支 → 报给核心 → **核心来判**（判必须在核心，否则约束能被绕） |
| **产出采集**（推进到评审中） | 核心读 git → 采不到（现在已改成留痕） | 执行端在**本地** git 上数 → 报给核心入库（采集点离代码近，可信度与今天相同） |

## 四、数据模型要动的地方

| 现在 | 改成 | 为什么 |
|---|---|---|
| `Project.RepoPath`（绝对路径） | **仓库身份**：`RepoRemote`（归一化的 remote URL）+ 仓库内相对目录 | 路径是**每个执行点本地解析**的事；同一份配置在每个人的机器上都成立 |
| `Project.RepoRemote`（只是显示用） | **绑定键** | 现在 remote 存着但不用，白存了 |
| `AccessCredential`（已有雏形） | 加「所属成员」 | agent 的动作要算在**谁**名下，审计里才查得到人 |
| —（缺） | **成员**（人）：名字 + 凭证 + 角色 | 共享 token 下谁都能批、谁进界面都是 owner |
| —（缺） | **审批归属**：该谁批 | 「审批只能个人批」的落点 |
| `AgentSession`（绑仓库路径） | 绑**仓库身份**（remote URL）+ 本地路径 | 会话绑定是 agent 侧的事实，不该用服务器路径来认 |

## 五、身份与账号（分三层）

| 层 | 是什么 | 现状 → 目标 |
|---|---|---|
| ① agent 的钥匙 | 凭证：签发时绑身份 + 可见项目 | 已有雏形 → 加「所属成员」 |
| ② 人的账号 | 成员（名字）+ 凭证 + 角色（owner / member / viewer） | 共享 token → 真正的成员 |
| ③ 归属 | agent 属于谁、审批该谁批、审计里「谁」是谁 | 自填 → 绑死 |

**git 身份的正确位置**（他问的第 2 条）：

| git 给的 | 是什么 | 用途 |
|---|---|---|
| **remote URL** | 仓库身份 | **自动绑定项目** —— 人不用再手填仓库路径 |
| **user.name / user.email** | 人的身份（本地 git 配置） | **名牌 + 第二因子**：凭证签发时绑定 git 身份，运行时报上来的必须对得上 |

**但 git 身份不是授权**：它是本地可改的文本，谁都能在 git config 里写别人的名字。
**凭证 = 授权（钥匙），git 身份 = 名牌。**

## 六、执行端 ↔ 核心 的协议

执行端对核心的调用只有四种：

1. **转发看板类调用** —— 核心现有的 MCP 工具（工具面不变）。
2. **要审批号** —— 写操作（`git_commit` / `git_push` / `shell_run`）前向核心申请；
   核心建审批 → 人在界面批 → 执行端带 `approvalId` 续跑。
   **这就是现在的续跑协议，不用新设计。**
3. **报本地读数** —— 当前分支、改动清单（产出采集）。
4. **身份对账** —— 连上来时报「我的 git 身份 + 我的仓库 remote」，核心核对。

## 七、分阶段（每一步都能单独用，都能回退）

### 阶段 0 · 账号与归属（不动执行模型，单机立刻更好用）
- 成员表：名字 + 凭证 + 角色
- 界面登录：token → cookie（沿用现在的）
- agent 凭证加「所属成员」；agent 发起的审批自动指派给它的主人
- 裁决时校验：只有归属人（或有权限的角色）能批
- **列表类工具按凭证范围过滤** —— 现在不传 projectId 就能列全公司的活（隔离的漏）

### 阶段 1 · 仓库身份化
- 项目绑「仓库身份（remote URL + 相对目录）」，路径降级为部署侧的事
- 会话绑定按 remote URL 匹配
- 凭证绑 git 身份；执行端/CLI 连上来时对账 + 自动绑定项目

### 阶段 2 · 执行点分离（本地 CLI）
- 新增 `guanfu agent mcp --core <核心地址>`：本地执行文件/git/shell + 读本地分支与改动 + 转发看板类调用
- 核心的 MCP 端点只留看板类工具；文件类工具移到执行端
- **单机形态不用变**：核心自己兼执行端（一个进程，工具在本地跑 —— 跟今天一样）
- 路径边界仍在：执行端本地解析仓库根（按 remote 匹配本机 clone），读不出仓库外

### 阶段 3 · 存储与多租户（团队规模需要时再做）
- SQLite → Postgres（多人写）
- 租户 / 工作区行级隔离
- 成员表换成公司的 SSO / OIDC

## 八、迁移路径（今天 → 目标态）

| 阶段 | 单机用户 | 团队用户 |
|---|---|---|
| 0 | 多个成员、各自凭证、审批只归自己 | 同左（核心还是本地） |
| 1 | 不用再手填绝对路径（配 remote 就行） | 同左 |
| 2 | **不用多跑进程**（核心兼执行端） | 每人机器上装执行端，核心在服务器 |
| 3 | 不变 | 多租户 + SSO |

**回退**：每个阶段都是加法 —— 阶段 0/1 不改执行模型；阶段 2 之后，单机形态仍然是一个进程。

## 九、诚实的边界（别让人误以为审批是强制门）

**审批闸门只管「观复 暴露的工具」。** agent 自己的客户端（Claude Code 的 Bash 等）
能绕过它 —— 今天就能绕（工具在服务端跑，agent 在本地有完整 shell）。

所以「审批只能个人批」在**平台内**（裁决、改配置、签发凭证、启动 agent）是可强制的；
在**agent 的本地动作**上不是 —— 那道门靠「agent 守规矩」+ 事后审计（哈希链里查得到）。

要真正强制，唯一的办法是**代码与命令只在观复能管到的地方执行**
（今天的单机形态，或执行端 —— 但 agent 仍然能绕过执行端用自己的 shell）。
除非把 agent 关进沙箱，那是另一个大工程。

## 十、还要你拍的

1. **侧车（执行端）这个形态接受吗？** —— 单机不受影响；团队要每人机器上多装一个。
2. **「功能一样」是「完全一样」（执行端）还是「基本一样」（远端关掉文件类工具）？**
3. **审批归属按谁算？** agent 凭证的所属成员？项目负责人？还是「两者取其一，有优先级」？
4. **成员表自己管，还是接公司的 SSO？**（阶段 3 之前至少要能自己管。）

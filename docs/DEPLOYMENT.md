# 部署形态：代码的执行点放在哪儿

> 这是一份**待决的评估**，不是已定的方案。
> 起因：2026-11-17 讨论「一台服务器给一个团队用」时暴露出一个前提 ——
> **人和 agent 都在各自本地干活，服务器上甚至没有代码、也没有 git。**
>
> 结论先行：观复 现在是**服务端执行**的工具（见下），
> 那个部署形态下有一半能力用不了。要变成团队工具，得先决定**执行点放哪儿**。

---

## 一、现在是什么形态（别被「本地设计」误导）

MCP 的工具是在**观复 服务所在的机器上**执行的：

| 工具 | 实际跑在哪 |
|---|---|
| `fs_read` / `fs_list` | 服务端（读 `Project.RepoPath` 指向的目录） |
| `git_commit` / `git_push` | 服务端（`IGitWriter` 调本机 git） |
| `shell_run` | 服务端（项目白名单里的命令） |
| `db_execute` / `db_query` | 服务端（连的是配置的数据库，数据库可以是共享的） |

所以「文件夹绑定 / git 记录 / 分支判断 / 工位 / 产出采集」这些能力
**要求观复所在的那台机器上有那个仓库**。

> 换句话说：**「本地设计」的准确含义是「代码在观复旁边」**。
> 单人本地跑观复时完全成立；服务器上只有看板时不成立。

---

## 二、「服务器上没有代码」时，现在这七样会怎样

| 现在有的 | 结果 | 表现 |
|---|---|---|
| `fs_read` / `fs_list` | 读不到目录 | 响亮失败（工具返回结构化错误） |
| `git_commit` / `git_push` | 同上 | 响亮失败 |
| `shell_run` | 命令跑得到，但不在 agent 旁边 | 半可用（跑在别人的机器上） |
| **分支验证**（`BranchGuard`） | 读不到 git →「读不到当前分支就拒绝」 | **响亮失败，且最狠**：绑了分支的活全都动不了 |
| **产出采集**（`FileChangeService`） | 采不到 | **静默失效**（采集失败不抛异常，账上少了产出但没人发现） |
| **工位 / worktree 独占** | 服务器上没有目录，没有对象 | 形同虚设 |
| `db_execute` / `db_query` | 数据库通常是共享的 | **成立** |

**仍然完全成立的**（全是纯数据）：任务 / 里程碑 / 依赖 / 状态机、三层规约、
评审骨架与 DoD 逐条判定、交接包与交接链、调度板、观复内的审批与审计、
用量统计、凭证与项目可见范围。

---

## 三、真正的问题不是「工具用不了」

是这个产品的承诺（见 `AGENTS.md` 开头）：

> 没人写代码的状态机叫流程图，没人签字的审批叫摆设，**没人能验的账叫日志**。

服务器上没有代码，agent 就用**它自己客户端的工具**改代码、跑 SQL ——
那些动作**完全不经过观复**。于是：

- 账上只剩「agent 说自己做了什么」；
- 「碰了哪个库、哪张表、改了哪些文件」从**查出来的**变成**自报的**；
- 审批闸门管不了 agent 的本地写操作 ——「不批就不执行」这句承诺在本地写上不成立。

**要继续当「agent 干活的账本」，就必须有一个在 agent 旁边的执行点。**

---

## 四、三个目标架构

### P1 · 纯看板 + agent 自带工具

观复 只管：看板、规约、评审、账本、审批（观复内的写）。
文件 / git / sql 交给 agent 自己的客户端工具（Claude Code 本来就有）。

- 产出改为 agent 自报（**标明来源是「自报」**），分支改为 agent 自报、观复 比对提醒。
- 代价：产出从「工作台自己数」降级成「agent 说」；账的性质变了。
- 工作量：中等，风险低。
- **单机部署时全功能不受影响**（服务器 = 本机，代码在旁边）。

### P2 · 中央看板 + 本地代理（sidecar）

开发者机器上跑一个轻量代理：文件 / git / shell 工具在**它**那里执行 ——
本地有代码 ✓，产出由**它自己从 git 数** ✓，分支由**它读本地 git** ✓。
写操作执行前先问中央「批了吗」，批了才执行 → **「不批就不执行」在本地写上照样成立** ✓。
所有调用上报中央，进哈希链。

- 代价：要写一个新进程 + 代理与中央的协议；MCP 客户端要指向代理（而不是中央）。
- 工作量：大。

### P3 · 每人本地一份观复，看板靠同步

现在的代码一行不改（单人场景全功能），但**多人的看板会分裂** ——
除非只有一个人用。共享看板是这个产品的核心价值，分裂了就没了。

### 一条中间路（我倾向的）

**P1 与 P2 不是二选一** —— 观复 本来就该支持两种部署：

- **单机部署**（人在自己机器上跑观复，仓库在旁边）→ 今天的全部能力成立。
- **中央部署**（服务器只有看板）→ 走 P1 的口径。

所以顺序可以是：

1. **先把部署形态显式化**（配置项 + 界面提示 + 文档）：
   中央形态下文件类工具**明确报错**「这台服务器上没有仓库，文件类工具不可用」，
   而不是让人对着「目录不存在」猜。产出采集失败也要**记一笔**（别静默）。
2. **再决定要不要上本地代理**（P2）——
   那时中央这边已经有账本、审批、规约的骨架了，代理只是把执行点搬回 agent 旁边。

---

## 五、要定的事（决策人自己拍）

1. **人改代码时用哪台机器？**
   - 自己的本地克隆（→ agent 的写操作在本地发生，服务器没有代码）
   - 服务器上的 worktree（远程编辑器 / Codespaces）→ 一切成立，现状不用改
2. **「产出可验」这件事值不值一个本地代理的工程量？**
   - 值 → P2
   - 不值（产出自报也能接受）→ P1
3. **团队规模与形态**：几个人？几个仓库？是否需要多租户？

---

## 六、现在就能做的（与决策无关）

- 单机部署的一切能力都是好的，继续在单机形态上打磨 agent 协作（工作包 / 分工 / 交接链）。
- 凭证体系（`/credentials`）与项目可见范围**两种形态都用得上** —— 已交付。
- 产出采集失败要**留痕**（这是 P1 之前就该修的）：现在它是静默的。
